## Key Code

`run_frontend_service.py:410-411` defines the session identity as raw string account plus buyer:
```python
return f"{str(account or '').strip()}\x00{str(buyer_id or '').strip()}"
```
`LocalSeatState.publish` (`748-977`) derives `shop_id` from the account, fills PDD missing accounts as `cs_<mall>:0`, and finally uses `_key(account, buyer_id)`. The only duplicate repair (`849-890`) runs when the new account is non-`local_`; it removes a local placeholder message from an old session only when the *same msg_id* exists there. It does not merge `主账号`, `pdd<mall>`, or other non-local display aliases into the canonical `cs_...` account, and it does not repair aliases when message IDs differ.

`run_frontend_service.py:1080-1093` visibility deliberately keeps only the seat account for each shop. This hides many remote accounts but does not canonicalize raw account strings. `merge_sessions` (`1106-1208`) also compares local and remote rows using the same raw `_key`, so a log alias and CDP canonical account cannot converge there.

`bridge/parser.py:232-256` has the strongest canonicalization: dict and textual `cs_<mall>_<uid>`, `cs-...`, and plain forms become `cs_<mall>:<uid>`. However `parse_line` (`977-1059`) first obtains one `account_hint = _extract_account(line)` and several logrus records emit that hint directly (`1045-1053`); the generic finalizer (`1110-1111`) only fills missing accounts with the hint. If `_extract_account` extracts a human display account (`主账号`/`pdd<mall>`) rather than a cs id, those paths preserve the alias. Blob paths call `_canonical_account` (`1179-1185`), but fallback to `account_hint` after canonical extraction, so the hint remains an alias when no explicit seller ID is present.

`bridge/agent.py:492-516` correctly selects one active feed and starts Tanyu logs only after CDP fallback; this prevents simultaneous source duplication but does not normalize identities across source changes. `bridge/channel.py:2264-2270` normalizes only send/open confirmation values, not all received event identities.

Existing test `test_v0514.py:727-766` proves only the narrow case: identical message ID first arrives under `local_pdd:pdd-agent-a`, then canonical `cs_427302374:164945148`; it asserts placeholder removal. No test covers `主账号`/`pdd<mall>` aliases, differing IDs, parser account hints, or CDP/log convergence.

## Architecture

PDD CDP events and Tanyu log events flow into `BridgeAgent._on_local_event`; the agent queues and pushes the same event to the local gateway. The gateway's `LocalSeatState.publish` is the authoritative local session store and floating-window source. It derives shop identity, stores sessions under `(account,buyer_id)`, and merges remote center rows using that same key. Therefore canonical identity must be established before `_key` in the gateway (or in every parser path), with alias-to-canonical mapping retained per shop. Feed selection avoids concurrent duplicate ingestion, but source fallback can still create duplicate sessions if aliases differ.

## Findings / Minimal Change Points

- **High – duplicate floating sessions remain possible:** `run_frontend_service.py:849-890` repairs only `local_*` placeholders and only matching `msg_id`; `主账号` and `pdd<mall>` are non-local and are never merged into `cs_<mall>:<uid>`. Minimal fix point: one PDD account resolver immediately before `shop_id`/`key` in `LocalSeatState.publish`, backed by `shop_accounts`/`seat_accounts`; migrate or merge any existing session for same `(shop_id,buyer_id)` into canonical account, independent of message ID.
- **High – merge layer preserves alias splits:** `run_frontend_service.py:410-411, 1140-1200` uses raw account keys for local/remote rows and detail summaries. Minimal fix point: use the same resolver in `_key` callers (prefer canonicalizing at publish and normalize remote rows before key comparisons); otherwise remote canonical rows remain unmatched to local aliases.
- **Medium – log fallback can emit aliases:** `bridge/parser.py:1045-1053, 1110-1111, 1180-1185` trusts `account_hint` without requiring/carrying a canonical seller ID. Minimal fix point: normalize `_extract_account` result or suppress PDD business messages lacking canonical `cs_` identity until shop/account metadata resolves it. Do not invent `cs_<mall>:0` at parser level.
- **Medium – send-side normalization is not receive-side normalization:** `bridge/channel.py:2264-2270` is scoped to send/open confirmation. Reuse/extract equivalent normalization in receive ingestion rather than adding another regex.
- **Low – existing source fallback is structurally correct:** `bridge/agent.py:492-516` starts only the effective feed. No change needed for concurrency; add identity convergence tests instead.

## Residual Risks

- A display alias without any mall/shop ID or seller/seat metadata cannot be safely mapped to a canonical `cs_` account; guessing would risk cross-shop conversation corruption. The resolver needs an explicit mapping or should quarantine such events.
- Existing persisted `seat.json` sessions require one-time in-memory migration plus save; normalizing only new events leaves old duplicate cards.
- Multiple CS seats/accounts per shop complicate “one session per buyer”: the correct uniqueness scope may be seat account, shop, or buyer. Current code explicitly scopes visibility to `seat_accounts[shop_id]`; preserve that policy while canonicalizing.
